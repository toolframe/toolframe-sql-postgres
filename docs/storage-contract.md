# Managed storage contract

A store is identified by `(application_id, stable_plugin_id)`. Each application
environment has a separate database. Each store has a business schema and a
private metadata schema. Worker generations and request roots are execution
identities, not data owners. Schema and role names are deterministic hashes;
role names also include the database identity because PostgreSQL roles are
cluster-wide. Restore preserves schema names and creates new destination roles.

## SDK and dialects

SDK 0.3 retains `Migration.sql` as the original SQLite SQL. Its checksum is
unchanged. Plugins declare PostgreSQL variants explicitly:

```python
Migration(
    revision="v1",
    sql="CREATE TABLE items(id INTEGER PRIMARY KEY AUTOINCREMENT, label TEXT)",
    dialects={"postgresql": "CREATE TABLE items(id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, label TEXT)"},
)
```

Every migration must supply a PostgreSQL variant. The provider hashes the selected
SQL and validates the full history before applying changes. This is not a general
SQLite translator. In particular PostgreSQL `REAL` has different precision from
SQLite `REAL`; first-party timestamp/value columns use `DOUBLE PRECISION`.

`StorageClient.execute_returning("INSERT ... RETURNING id", parameters)` returns
`{"rows": [{"id": 1}], "rowcount": 1}` on both SQLite and PostgreSQL.
PostgreSQL `execute` returns `lastrowid: null`; use `RETURNING` for generated IDs.

## SQL surface

- One SELECT for `query`; INSERT/UPDATE/DELETE for `execute` and
  `execute_returning`. Returning mutations must use `execute_returning`.
- Qmark parameters (`?`), positional JSON values, unqualified store-owned tables.
  Quotes, doubled quotes and comments are handled before PostgreSQL AST parsing.
  Dollar placeholders/quoting, escaped string literals and JSON question-mark
  operators are outside this contract; bind values as parameters.
- A bounded set of ordinary builtins, defined in `sql.py`; schema-qualified
  functions, catalog/private tables, role/session commands, SELECT INTO, explicit
  row locks and write CTEs in read-only queries are rejected.
- Migrations accept transactional store-local table/index CREATE/ALTER/DROP and
  data mutations. Arbitrary functions, extensions, schema changes, privileges,
  concurrent index creation and transaction statements are unsupported.
- Results must be JSON-compatible, at most 10,000 rows and below the RPC byte
  budget. Cast decimals/timestamps/UUIDs to supported JSON scalar types in SQL
  where needed. Use LIMIT and pagination.

PostgreSQL grants enforce cross-store table isolation even if application SQL is
incorrect. Business roles have DML privileges but no schema DDL or metadata access.
The SQL guard narrows the supported contract; it does not claim to sandbox arbitrary
Python, SQL or database administrators. The database must remain operator-controlled.

## Transactions and acknowledgement loss

Connections are bounded; a transaction retains one connection. Writes acquire an
owner advisory transaction lock. Transactions are bound to their Core-issued
owner, generation, root and deadline. Nested transactions are rejected. Any failed
statement poisons the transaction; roll it back. Cancellation, root cleanup,
expiry and provider shutdown close the connection and roll back uncommitted work.

Standalone mutations and transaction commits write a durable receipt in the same
PostgreSQL transaction. Supply a stable mutation ID when reconciling retries. A
replayed standalone mutation returns its original result; changed SQL/parameters
with the same ID is a conflict. After an uncertain commit, discard its transaction
token and ask `storage.receipt(mutation_id)` in a new admitted call. Repeating
`begin` with that ID reports an already committed mutation. Never infer rollback
from a lost network acknowledgement. Receipts are retained without automatic
pruning in this release.

These contracts support one Core per application. PostgreSQL-backed plugin data
alone does not coordinate Core workers or transient browser/MCP contexts across
replicas. Core's independent journal can use SQLite or, from Core 0.6, a dedicated
PostgreSQL database. It is not part of the provider's database or backups.
